# 系统架构

## 架构目标

在不推倒现有 Godot 4.7 横版战役的前提下，把叙事内容、CampaignLevel 流程、角色战斗、面具配置及表现反馈拆成可替换边界。旧有流程仍是主干；新增内容通过数据与事件挂接，不把 `main.gd` 变成所有战斗、剧情和存档规则的总控制器。

**兼容声明：**目前未读取项目源码。下述是可供程序核对的目标契约；实际节点树、信号名和 JSON 字段须先盘点，再以最小改动映射，不应将建议字段误认为项目已有接口。

## 系统地图

| 子系统 | 主要职责 | 主要入口／出口 |
|---|---|---|
| 战役流程与场景协调 | 标题页、序章、四幕关卡、检查点、胜败转场、结局页 | `main.gd` 负责启动／顶层切场；`CampaignLevel` 负责当前关卡内流程与结果上报 |
| 玩家与战斗 | 移动、剑／雷／盾、受击、契息、Boss 姿态与伤害结算 | 玩家／敌人场景发出战斗意图，经既有 `DamageAndHealth` 生命边界结算 |
| 敌人及 Boss | 普通敌人状态机、预警、Boss 阶段、弱点与战斗结果 | 接收战斗输入及关卡状态；向战斗／战役层发出死亡、阶段和胜败事件 |
| 岁契与进度 | 面具定义、解锁、主契／辅契配置、检查点进度、幕推进 | 由关卡结果更新；将确定后的配置提供给玩家战斗系统 |
| 剧情与呈现 | JSON 剧情解析／显示、UI、动画、音效、镜头及命中反馈 | 订阅对话、战斗、Boss 与进度事件；原则上不反向决定伤害或剧情进度 |

## 系统职责

### 战役流程与场景协调

- `main.gd` 保持启动入口、全局服务创建、标题／战役入口与顶层场景切换职责。它不直接处理玩家攻击、Boss 阶段或 JSON 台词分支。
- 每个 `CampaignLevel` 保留本幕关卡身份、场景内出生点／检查点、遭遇触发器、Boss 引用和胜败出口；关卡完成时报告明确结果，由战役流程判定下一幕或结局。
- 重试应从当前关卡的最近检查点恢复，不重新创建一套不一致的全局战役状态。

### 玩家与战斗

- 玩家动作只表达移动／攻击／格挡／释放技能的请求；命中由现有碰撞／攻击窗口确定，再交给生命与伤害边界处理。
- `DamageAndHealth` 继续负责生命值边界、伤害接收、死亡判定与对应信号；不要把面具选择、剧情解锁、Boss 多阶段或 UI 塞入该组件。
- 面具效果由数据配置与战斗效果处理共同承担；效果只在规定的战斗事件触发，不直接修改 CampaignLevel。

### 敌人、岁契与呈现

- Boss 自己管理阶段、预警、攻击窗口、破绽和姿态值；HP 仍走通用伤害边界。姿态破防是 Boss 战斗状态，不等同于生命伤害。
- 面具数据定义唯一 ID、显示内容、主动技成本／冷却、被动触发条件、效果参数、解锁条件及表现资源引用。解锁状态属于进度数据，当前装备属于会话／存档配置。
- JSON 剧情记录可显示文本、说话者、演出标记与已约定的剧情旗标；解析／展示层不负责执行玩家伤害、给 Boss 扣血或直接跳到下一幕。若旧格式已有动作字段，应先保留兼容映射，再渐进规范化。
- UI、动画、音效、震屏和特效订阅统一的“命中、精准格挡、受击、破防、面具触发、Boss 阶段变化、检查点、胜利／失败”等反馈事件；视觉效果不成为玩法判定源。

## 依赖关系

```text
main.gd（启动、顶层切场）
  └─ 战役流程 / CampaignLevel
       ├─ 剧情 JSON 展示
       ├─ 检查点与战役进度
       ├─ 玩家战斗 ── 面具配置与战斗效果
       └─ 普通敌人／Boss ── DamageAndHealth
战斗与流程事件 ── UI / 动画 / 音效 / 镜头反馈
```

依赖原则：

1. `DamageAndHealth` 不依赖面具、剧情或 UI；上层可以订阅它的结果。
2. Boss 阶段只依赖自身状态、战斗事件与玩家能力规则；不直接改写 JSON 或主场景状态。
3. 战役进度只在明确的检查点／Boss 胜利／幕结束事务上写入；普通攻击不能修改解锁状态。
4. 面具效果依赖玩家战斗事件和面具配置；UI 读取配置与状态，不拥有状态。
5. 任何新的资源预载、对话推进或场景切换由既有流程负责，避免互相直接调用形成循环依赖。

## 资源、状态与信息流

建议规范化的战役状态模型（字段名是设计建议，按现有项目命名适配）：

| 状态 | 归属 | 写入时机 | 主要消费者 |
|---|---|---|---|
| 当前幕／关卡／检查点 ID | 战役进度 | 进入关卡、触发检查点 | `main.gd`、CampaignLevel、继续游戏入口 |
| 已完成 Boss ID 集合 | 战役进度 | Boss 胜利确认后 | 幕推进、剧情旗标、面具解锁 |
| 已解锁面具 ID 集合 | 战役进度 | 对应胜利演出／领取奖励后 | 面具 UI、配置校验 |
| 主契 ID、辅契 ID | 玩家配置 | 检查点换装并确认 | 玩家战斗初始化 |
| 当前 HP、契息、受击／冷却状态 | 当前战斗会话 | 战斗事件 | 玩家、UI、重试初始化 |
| Boss 阶段、HP、姿态、预警 ID | Boss 实例 | Boss 状态机事件 | Boss 动画、UI、反馈层 |
| 剧情旗标／对话节点 ID | 剧情／战役进度 | 对话节点明确提交 | JSON 剧情条件与后续演出 |

推荐信息流：CampaignLevel 装载关卡身份与检查点 → 战役进度提供已解锁面具和当前配置 → 玩家／敌人运行战斗 → 命中事件提交 `DamageAndHealth`，战斗事件同时供面具效果与反馈消费 → Boss 胜利由关卡流程接收并确认 → 保存 Boss／面具／剧情旗标 → 播放 JSON 胜利剧情 → 推进下一幕或结局。重试只恢复检查点定义的状态；不应因重试重复发放面具或重复推进剧情旗标。

面具数据最小字段建议：`id`、`display_name`、`unlock_boss_id`、`active_cost`、`active_cooldown`、`active_effect_id`、`passive_trigger_id`、`passive_effect_id`、效果参数、图标／动画／音效资源引用、文本本地化键。剧情 JSON 使用稳定的剧情 ID 与旗标 ID，不以显示文本作为逻辑键。

## 核心循环覆盖

| 核心循环节点 | 负责系统 |
|---|---|
| 标题页／序章／幕间／结局的场景入口 | `main.gd` 与战役流程 |
| 横版移动、战斗、受击和死亡 | 玩家与战斗、`DamageAndHealth` |
| 普通敌人与四个 Boss 的战斗阶段 | 敌人及 Boss、战斗系统 |
| 检查点重试、胜利推进与面具解锁 | 战役流程、进度系统 |
| JSON 剧情播放及旗标更新 | 剧情层、战役进度 |
| 打击、预警、震屏及 UI 反馈 | 呈现层订阅战斗／流程事件 |

## 系统边界

**保留并适配：**`CampaignLevel` 的关卡驱动与四幕流程；`main.gd` 的根入口；已有 JSON 剧情数据；失败重试、胜利剧情和结局转场；`DamageAndHealth` 的通用生命／死亡语义；普通敌人、四个 Boss、Debug Runner 和无头测试入口。

**优先扩展而非替换：**新增面具配置与进度状态、Boss 姿态／弱点、可被 UI 和音频读取的战斗事件；手感参数应数据化或集中调节，避免各场景复制不一致常数。

**不属于本次架构目标：**重写引擎级物理、引入大型装备数据库、完整任务编辑器、通用可视化对话工具或把所有系统改成全局单例。若既有实现与建议冲突，先维持可运行路径，提取窄接口后再迁移。

## 优先级与范围

1. **兼容优先：**盘点现有场景／信号／JSON／测试入口；确保原四幕仍可从标题页走完。
2. **闭环优先：**新增一张面具的数据、装备、战斗触发、反馈和战后解锁端到端闭环。
3. **扩展复用：**以相同数据结构接入其余三张面具与三个 Boss；用检查表保证每个 Boss 阶段可读。
4. **内容替换：**再迁移整套中文剧情、UI 文本、美术、音频资源，不在迁移中混合重写底层生命／伤害代码。

建议保留现有无头测试／Debug Runner，并增加面具事件、Boss 胜利仅触发一次、检查点重试状态一致、JSON 剧情关键旗标、全战役场景可达性等自动化验收项。性能预算、具体平台和存档格式需依项目目标平台确认。

## 开放的结构问题

- **必须工程核对：**`CampaignLevel` 当前如何表示幕序、检查点和胜败；`main.gd` 是否承担超出根协调的职责；`DamageAndHealth` 是否允许携带伤害来源／标签；现有 JSON 是否有分支旗标。
- **待确认内容契约：**现有雷击和护盾究竟是持续输入、单次技能还是多模式输入；本设计的帧窗与成本须映射到既有输入，不额外制造冲突操作。
- **待确认存档兼容：**重构后旧存档的关卡 ID、Boss ID 或剧情旗标是否迁移；若无现有用户存档需求，可在立项时将旧存档兼容列为非目标。
